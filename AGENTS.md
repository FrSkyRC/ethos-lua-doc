# Agent guide: ethos-lua-doc

MkDocs (Material) site documenting the FrSky Ethos Lua API, published to GitHub Pages. Most of the API reference is **generated** from upstream sources; guides, best practice and the cookbook are **hand-written**.

Read this before changing anything. The most common mistake is editing generated files.

## Repository map

| Path | What | Edit by hand? |
| --- | --- | --- |
| `docs/api/**` | API reference: one page per function, plus `SUMMARY.md` nav and `api-index.json` | **No.** Generated by `scripts/gen_api_pages.py` |
| `docs/examples/official/**` | FrSky's official example scripts as pages | **No.** Generated by `scripts/sync_examples.py` |
| `data/api.json` | Parsed API (source of truth for `docs/api`) | **No.** Generated by `scripts/parse_lua_doc.py` |
| `data/usage.json` | Real-world call snippets from public projects | **No.** Generated by `scripts/scan_usage.py` |
| `data/upstream.json` | Where upstream sources come from: channel, `lua-doc.zip` URL, repos to scan | Yes |
| `overlays/api/<owner>/<member>.md` | Curated examples/notes merged into a generated API page | **Yes**, this is where API examples go |
| `overlays/api/<owner>/index.md` | Extra prose for a namespace/object overview page | Yes |
| `examples/cookbook/<folder>/main.lua` | Cookbook scripts, embedded into `docs/cookbook/*.md` with `--8<--` | Yes, and test them (below) |
| `docs/**` (everything else) | Hand-written guides, best practice, tools, contributing | Yes |
| `docs/SUMMARY.md` | Top-level nav (literate-nav) | Yes |
| `hooks/*.py` | MkDocs hooks: overlay edit links, `llms.txt` | Yes |

`<owner>` is a namespace name (`lcd`, `system`, `form`, ...) or an object class (`Source`, `Timer`, `NumberEditLib`, ...), exactly as in `data/api.json`.

## Upstream sources and how to get the latest

### 1. `lua-doc.zip`: the API itself

- **Where:** release assets of [FrSkyRC/ETHOS-Feedback-Community](https://github.com/FrSkyRC/ETHOS-Feedback-Community/releases). Every Ethos release (`26.1.2`, `1.6.8`, ...) has a `lua-doc.zip`, and so do the rolling nightly releases (`nightly26`, ...).
- **The "latest" location changes with each Ethos release.** There is no fixed URL. Nightly assets are replaced in place under the same tag as new nightlies build, and a new major series gets a new tag (`nightly26` → `nightly27`). Stable releases each get their own tag.
- **So never hard-code the URL.** `scripts/update.py` discovers it through the GitHub releases API, according to `channel` in `data/upstream.json`:
    - `nightly` (default): the highest-numbered `nightlyNN` release that has `lua-doc.zip`, so the docs cover the newest API.
    - `stable`: the **highest version number** among non-prerelease releases with `lua-doc.zip`. Not the newest by date: FrSky also ships maintenance releases of older lines, such as `1.6.8` published after `26.1.2`.
    - `pinned`: exactly `lua_doc_url`.
- After a run, `lua_doc_url` in `data/upstream.json` records the URL actually used, and `data/api.json` → `source` records the release tag, sha256 and fetch date. The API index page shows them.
- **Format:** Doxygen 1.9.x HTML (no XML). `scripts/parse_lua_doc.py` reads `namespace*.html` and `class*.html` (`memitem` blocks: brief, `since`, params table, return, code fragments) plus `index.html` for the intro. If FrSky changes Doxygen versions or templates, this parser is what breaks. Check its summary line (`parsed N namespaces, N classes, N functions, N constants`) against the previous run.

### 2. Official examples

- `lua/examples/` in the same repo, on its **default branch**. That branch is named after the current release (`26.1` at the time of writing), so don't hard-code `master`. `update.py` sparse-clones just that folder.

### 3. Real-world usage

- Public repos listed in `data/upstream.json` → `usage_repos`, shallow-cloned on their default branch, or on `branch` if set. `path` limits the scan to a subfolder and triggers a sparse clone; use it for big repos.
- Snippets link to the **exact commit**, so links stay valid.
- To add a project: append `{"repo": "owner/name", "label": "Display name"}`, and run the update.

## Updating (do this regularly)

```bash
python -m venv .venv && .venv/bin/pip install -r requirements.txt      # Windows: .venv\Scripts\...
python scripts/update.py                  # discover + download lua-doc.zip, examples, usage; regenerate
git diff --stat                           # review
mkdocs build --strict && python scripts/check_site.py   # both must pass
```

Flags: `--channel stable|nightly|pinned`, `--url <zip>`, `--zip <local file>`, `--examples <local lua/examples dir>`, `--skip-examples`, `--skip-usage`.

The `update-lua-doc` GitHub workflow runs the same thing weekly (and on demand) and opens a PR when anything changed.

### Reviewing an update

1. `data/api.json` diff: new functions (new `since` values), changed params or returns, removed functions.
2. If a function **disappeared**, check whether a guide, overlay or cookbook script still links to it. `mkdocs build --strict` fails on broken links to removed pages.
3. If a new Ethos version adds an API, consider adding an overlay example and mentioning it in the relevant guide.
4. Overlays for removed functions are orphaned and silently unused. Delete them or move the content.

## Writing content

### API examples → overlays

Create `overlays/api/<owner>/<member>.md`. Plain Markdown, inserted under **Examples** on the generated page, above the upstream examples. Then run `python scripts/gen_api_pages.py` (fast, no network). Keep examples short, runnable and correct; prefer patterns from `docs/best-practice/`.

### Accuracy rules

- **Don't name third-party projects as sources** in site content (no "Rotorflight found...", no project names on usage tabs or the usage page). Say "open-source Ethos Lua projects" or "one large project". The project list lives only in `data/upstream.json`.

- **Don't invent API behavior.** Check `data/api.json`, the official examples, and real usage (`.cache/usage/**` after an update, or `data/usage.json`). If you can't verify something, test it in the simulator, or leave it out.
- Behavior verified in the simulator is worth recording, with how it was verified. Example: relative paths in callbacks resolve against the last-loaded script.
- Measured RAM numbers must name their source (radio, project, what was measured).

### Cookbook scripts must be tested

1. Put the script in `examples/cookbook/<folder>/main.lua` (folder name ≤ a few chars is fine; the widget `key` must be ≤ 7 chars).
2. Boot it in the simulator with [FrSkyRC/ethos-tools](https://github.com/FrSkyRC/ethos-tools) (`simulation/run_wasm.js`, or the Claude Code plugin `ethos-simulator@ethos-tools`). The process is described in `docs/tools/ai-agents.md`.
3. Required: no errors in `node run_wasm.js log` after boot. For widgets and tools, also place or open them and screenshot.
4. Delete stale `*.luac` before each boot: Ethos compiles `main.lua` to `main.luac` on load.

## Build and preview

```bash
mkdocs serve          # http://127.0.0.1:8000
mkdocs build --strict
```

`pymdownx.snippets` paths (`--8<-- "examples/..."`) are relative to the repo root, so run mkdocs from the root.

## Releases (the version on the site's repo button)

Material shows the repo's **latest GitHub release tag** next to the repo name in the header (as on ethos-doc.frsky-rc.com). Tag releases by the Ethos version the docs cover: `26.1` now. When the API moves to a new Ethos line (e.g. the updater switches to `nightly27`), publish a new release:

```bash
gh release create 27.1 --target main --title "Ethos 27.1 Lua docs" --notes "..."
```

## Conventions

- Site URL and repo: `mkdocs.yml` (`site_url`, `repo_url`). The hooks and the overlay edit links depend on `repo_url`.
- Brand colors are shared with the Ethos manual site (`docs/stylesheets/extra.css`).
- Python ≥ 3.12 for scripts (uses `shutil.rmtree(onexc=)`).
- Run Python on downloaded content with `-I` (isolated mode), as `update.py` does.
